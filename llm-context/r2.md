## How Diletta uses it

- One bucket per env, bound as `FILES_BUCKET`: `diletta-files-staging`, `diletta-files-production` (created by hand, `docs/runbooks/knowledge.md`); local dev and tests use miniflare's local bucket (`diletta-files-local`, never remote).
- Every object has a `files` row (the registry) and lives at `fileR2Key(company public_id, file public_id)` = `t/{company}/{file}` (`packages/schemas/src/files/`). The key is derived, never stored.
- Only `providers/fileStorage.ts` touches the bucket in app code (`put` with `httpMetadata.contentType`, `get`, `delete` in batches of ≤ 1000 keys); tests may read it to check objects. It never throws and logs keys and sizes, never bytes.
- Order: an object's bytes never change. New bytes are a new file: the object is written first (named by a publicId the Repo generates, outside any lock), then its row in a transaction; if the transaction doesn't store it, the object is deleted. A replaced or deleted file's object goes after the commit. So a failure can leave an object with no row, never a row whose object is missing or holds other bytes.
- First user: knowledge documents (M2-5), one object per document version: a changed page gets a new file and the old object is deleted. Chat images, eval transcripts and exports add their owner types when they land.
