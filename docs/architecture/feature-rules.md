# Feature rules

> Per-feature invariants moved out of `CLAUDE.md` to keep it short. Read the section for the feature you touch, plus its runbook. Same authority as `CLAUDE.md`; `.github/pattern-rules.md` enforces them.

## Widget and conversation

- **Widget auth (M2-1, ADR 0001)**: `GET /widget/ws` takes the companion JWT in `Sec-WebSocket-Protocol` (`['diletta.v1', <jwt>]`), never in the URL, and decides everything before the upgrade. Only `WidgetAuthRepo.authenticate` turns it into a `WidgetIdentity` (server-side, internal ids): alg allowlist RS256/ES256 + `kid`, no `crit` → issuer → `company_connections` (`withPlatform`) → signature on the issuer's JWKS (`JwksProvider`, KV `JWKS_CACHE`, fetched only for a registered issuer, size-capped) → `aud = WIDGET_JWT_AUDIENCE`, `exp`/`nbf`/`iat`, lifetime ≤ 5 min → connection active + `Origin` in `allowed_origins` → active company and chatbot (`withTenant`). Every failure before the signature passes is 401, so only a signed token can see 403/404. Failures are HTTP statuses (`WIDGET_AUTH_FAILURE_HTTP_STATUS_MAP`) with a generic body; the answer selects `diletta.v1` only. `GET /widget/bootstrap` (M2-7, ADR 0002) takes the same token as `Authorization: Bearer` (scheme in any case) through the same `authenticate`, reads only (`WidgetBootstrapRepo`: chatbot name + published config's `widget` block, `widget: null` without one) and creates nothing; `/widget/*` sets its own CORS (any origin, no credentials, only `Authorization`), the data gated by `allowed_origins`. Both routes validate their query only after `authenticate`, so no valid token = 401 whatever the query.
- **Conversation DO (M2-2)**: `ConversationsRepo.startOrResume` (worker, after auth) upserts the `chatbot_users` row and creates the conversation (with a `conversation.started` critical event as `root_log_id`) or resumes the user's own open one (else `ConversationStartFailureEnum.NotFound` → 404). The worker then forwards the upgrade to `ConversationDO` (`getAgentByName`, name = `conversations.public_id`) with a fresh header set carrying the session (`CONVERSATION_SESSION_HEADER`), and closes a conversation it just created if that upgrade fails; the DO has no public route. The DO extends Think, locked down: no workspace bash or MCP, its tools are `search_help_docs` (M2-6; active only when the bot lists knowledge sources) and the config's pinned host tools (M3-4), no reasoning or identity frames, `onChatError` returns safe text only. Every inbound frame passes `WidgetFrameProvider.admit` (pure, unit-tested): a chat request is rebuilt to its newest user message with a new id; cancel and stream resume pass; the widget's own `feedback` frame (M2-7) is stored by the DO (read model synced first, then `FeedbackRepo.recordFeedback` on a synced reply of this conversation, one row per reply per user, answered `{type:"feedback", rating | null}`; `recordFeedback` re-checks the conversation open and the company and chatbot active, refused while closing, at most `FEEDBACK_FRAMES_PER_WINDOW` per conversation per minute, stored one at a time in arrival order); everything else is refused. The `conversation` frame carries the ratings already given (the newest `CONVERSATION_FEEDBACK_MAX_RATINGS` replies', each entry parsed on its own), which the worker reads before the upgrade (`CONVERSATION_FEEDBACK_HEADER`), so connecting costs the DO no database read (except to resend open change requests, M3-4). One turn at a time, refused while closing; the turn's ULID (`Utility.generateUlid`) and the activity time are stored at admission, then `loadTurnConfig` re-checks the conversation, chatbot and company and loads the published config (so a publish or a pause takes effect at the next message) and the model is routed; any failure → `{type:"unavailable"}` (or `closed`), nothing saved. `webSocketMessage` initializes the DO (`__unsafe_ensureInitialized`) before checking a frame, so after a hibernation wake the reused-id check sees the stored transcript. The read model is synced from the transcript (`TranscriptProvider`, position = the last synced message id, never an index) after every turn and, in `waitUntil`, on every wake, so a failed write or an evicted turn is caught up; `recordTurn` is idempotent on `session_message_id`. A conversation never closes over an unsynced backlog. A turn Think ends without a hook is released in a `finally` around the frame's dispatch. Auto-close after `CONVERSATION_IDLE_CLOSE_MS` (DO schedule, never sooner than `CONVERSATION_CLOSE_RETRY_MS` from now): Closed, Answered or Abandoned. DO runtime state goes through `patchRuntimeState` (no await between read and write).
- **Widget UI (M2-7)**: `apps/widget`, one store per widget (`createWidgetStore`), never a module singleton. Hooks turn Think's transcript and the DO's frames into `Schemas.WidgetPanelView`; components only render it (the dev gallery `?gallery` draws every state from sample data). Every DO frame is parsed with `ZWidgetServerMessage`, every tool output with its schema, before use. The socket opens only for a first message or a saved conversation (never on page load); a new conversation id is saved and the session remounted with it (`ChatSession` keyed by id) before anything is sent; a saved conversation the server keeps refusing is dropped and the widget goes idle (`lib/connectFailures.ts`; a failed `getToken` counts but never drops it). `getToken` is called for every connect and every bootstrap read, the token never stored; each token tells the store the host user (SHA-256 of `sub`, `lib/hostUser.ts`), which keys the saved id. `DilettaWidget` gets a fresh store per apiBase + chatbot; the script tag's controllers act only on their own widget. Widget types and props live in `WidgetUi.ts`; sizes off the preset scale are `@theme` tokens in `widget.css` (`text-widget-*`, `rounded-widget-*`), kept out of `cn()` next to a text colour. Markdown is the widget's own safe parser (`lib/markdown.ts`: no HTML, links only http(s)/mailto). Review cards (M3-5) render `Schemas.WidgetChangeCardView` only; their actions live in `hooks/useChangeReview.ts`. Styles go into the shadow root through `prepareShadowCss` (`:root` → `:host`, rem → px, `@property` hoisted); the host document gets only the `@property` rules and the fonts link. The script-tag bundle stays under `WIDGET_BUNDLE_MAX_GZIP_BYTES` (the build fails above it). Runbook: `docs/runbooks/widget.md`.

## Dashboard pages

- **Dashboard shell (M4-1)**: `_authenticated/route.tsx` reads `/dashboard/me` (`useMe`) before any page: loading, error with retry, No access (403, or an operator: the dashboard is company-level), else the shadcn `Sidebar` (`collapsible="icon"`) + top bar + page. Navigation lives only in `_authenticated/-nav.ts` (sidebar and breadcrumb just map it; an item with `items` is a nested group, like Settings); a new page = its entry there + its route under `_authenticated/` (Settings pages under `settings/`). The `me` key carries the Clerk user id; a failed background refetch keeps the loaded admin (only the first load or a 403 replaces the shell). The icon-rail state persists in shadcn's `sidebar_state` cookie, read on mount; the mobile Sheet closes on navigation. Every page opens with `components/page-header` (props in `Schemas.DashboardUi`). No bot switcher (DESIGN.md §6). The environment badge reads `VITE_APP_ENV` (set in the deploy workflows).
- **Insights pages (M4-3)**: Overview, Usage and Impact read `activity_rollups` only through `GET /dashboard/insights/{overview,usage,impact}` (`authorizeCompany(InsightRead)`, `range` + optional `botId` = chatbot public id, unknown → 404) → `InsightsRepo` (one read-only `withTenant`; one owner's rows: the bot's, else the company-wide `chatbot_id` null rows, never summed across chatbots) → `ActivityRollupsDAL.getActivityRollups`. Keys are read back only through `Schemas.parseActivityRollupMetric`; the math is pure in `InsightsProvider` (unit-tested): spend = the `.model.` cost keys of company-key providers (live + eval; Workers AI is "Included", never spend), costs summed as bigint micros, a platform task (search) is Search in either scope and any other eval call is a test run. Readings are indexed by day once (`InsightsProvider.indexReadings`), never rescanned per metric or day. Ranges and periods only from `Schemas.insightsRangePeriods` / `impactRangePeriods` / `insightsBillingMonth` (UTC; the Overview spend card is the company's billing month from the company-wide rows, whatever the range or `botId`). Needs attention and the live config are read now from their own tables. Impact tasks = `answers` (conversations answered) + `tool:<name>` per write tool (verified − the user's undos (`user_undone`), never an auto-undo, which was never verified; never below 0 over the range), each day valued at `Schemas.roiMinutesOnDay`, weekly bars spread so they add up to the range (`InsightsProvider.spreadWeeks`); minutes are saved only by `POST /dashboard/roi-assumptions` (`RoiAssumptionUpdate`): a new `roi_assumptions` row in force from today, never an update. Pages keep the range in the URL (`ZInsightsPageSearch` / `ZImpactPageSearch`), and share `components/metric-strip`, `range-select`, `bar-chart`, `section-header`, `page-state`. Runbook: `docs/runbooks/rollups.md`.
- **Conversations page (M4-4)**: list + transcript read only through `GET /dashboard/conversations` (paged, `ZGetConversationsApiRequest`: `tab` all / needs_attention / rated_down, `outcome` incl. `in_progress`, `configId` = a published chatbot config's public id, `botId`; unknown → 404), `/export` (same filters, ≤ `CONVERSATIONS_EXPORT_MAX_ROWS`, the browser builds the CSV with `Utilities.toCsv`, formulas defused) and `/:publicId` (`authorizeCompany(ConversationRead)`) → `DashboardConversationsRepo` (one read-only `withTenant`). Needs attention = a NeedsHuman change request or an open quality issue; Rated down = any Down reply; every tab's count in one query. The transcript never carries args, a change's values or a host answer (nothing decrypted): a tool row is name, version, status (`TOOL_CALL_ERROR_LABEL_MAP`) and the change request's `summary` + status (`CHANGE_REQUEST_ERROR_LABEL_MAP`). Turns and costs only in `ConversationTranscriptProvider` (pure, unit-tested): a turn = one `turn_id` across messages, tool calls and spend model calls, ordered by its first row; its cost = `SUM(model_calls.cost_usd)` by `turn_id` with `provider <> workers_ai` (as Usage's spend), bigint micros, Pending / Unknown noted (`ConversationCostNoteEnum`); the conversation's total adds calls with no turn. A purged conversation keeps its row and costs, not its title or text. Flag = `POST /dashboard/conversations/:publicId/flag` (`authorizeCompany(QualityIssueCreate)`, `QualityIssuesRepo.flagConversation`): one open admin issue per conversation (advisory lock; a repeat returns it, 200), `quality_issue.opened` (actor Admin) in the same `withTenant`, relayed after the commit. Open change = `/changes/$id` → `GET /dashboard/change-requests/:publicId` (`authorizeCompany(ChangeRequestRead)`, `ChangeRequestsRepo`, never its values; the Changes page, M4-5). Pages: `/conversations` and `/conversations/$id` (list in 2 columns, detail card in the third at ≥1100px), filters + page in the URL (`ZConversationsPageSearch`); chips through `components/status-chip`, dropdown filters through `components/filter-select`. Runbook: `docs/runbooks/conversations.md`.
- **Changes page (M4-5)**: list + detail read only through `GET /dashboard/change-requests` (paged, `ZGetChangeRequestsApiRequest`: `tab` all / waiting / verified / undone / needs_human (`CHANGE_REQUEST_TAB_STATUSES`: Waiting = not ended (Proposed, Approved, Committing, Committed, Mismatch); Rejected, Expired, Failed and Resolved only under All), `requesterId` = the chatbot user's host user id (one lookup on its unique index), `botId`; unknown → 404 (the page shows it as no matches); every tab's count in the same answer), `/requesters` (the Requested by choices: top `CHANGE_REQUEST_REQUESTERS_MAX` by change count, plus the one the URL picked; its own query, long `staleTime`), `/needs-human-count` (the sidebar's Changes badge, `-nav.ts` `badge` → `NAV_BADGES` in `-AppSidebar.tsx`, one component per badge reading only its own query; a 6px dot in the icon rail) and `/:publicId` (`authorizeCompany(ChangeRequestRead)`) → `ChangeRequestsRepo` (one `withTenant`). Never a change's values (no per-record diff): summary, why (`errorLabel`), tool, records, the conversation, and the timeline = the change request's `activity_log` events (`ActivityLogDAL.getActivityLogTimeline`, actor names joined; capped at `CHANGE_REQUEST_TIMELINE_MAX_EVENTS` keeping the newest) in words by `ChangeRequestTimelineProvider` (pure, unit-tested; details through `Schemas.ZChangeRequestEventDetail`). Mark resolved = `POST /dashboard/change-requests/:publicId/resolve` (`authorizeCompany(ChangeRequestResolve)`, `resolveChangeRequest`): row locked, NeedsHuman → `Resolved` (12) only (else 409 `NotNeedsHuman`, nothing written), `undo_until` = now (`ChangeRequestsProvider.undoUntil`, so the purge empties its values), `change_request.resolved` (actor Admin) in the same `withTenant`, relayed after the commit; the answer's detail is read after the commit (a failed read never rolls back the resolve: the change comes back with an empty timeline); Resolved is final, and the widget / model read it like NeedsHuman. Pages: `/changes` and `/changes/$id` (list in 2 columns, detail card in the third at ≥1100px), filters + page in the URL (`ZChangesPageSearch`). Runbook: `docs/runbooks/actions.md`.
- **Quality page (M4-6)**: inbox read only through `GET /dashboard/quality-issues` (paged, `ZGetQualityIssuesApiRequest`: `tab` open / converted / fixed / dismissed (one status each, absent = Open), `botId`; unknown → 404; every tab's count in the same answer), `/open-count` (the sidebar's Quality badge, warning) and `/:publicId` (`authorizeCompany(QualityIssueRead)`) → `QualityIssuesRepo` (one `withTenant`). A row = the conversation's title, type chip ("Not triaged" while `issue_type` is null), the note or else the rated reply's start, source ("From a user" / "From an admin" / "Automatic check"); the detail adds the excerpt (`QualityIssuesProvider`, pure, from `MessagesDAL.listRecentChatMessages`: the newest `EVAL_CASE_MAX_MESSAGES + 1` user / assistant texts up to the rated reply, never the whole chat; the rated reply and the question before it for a user issue, never another reply in its place; else the last answered turn, or a trailing question nobody answered; none once purged, `isContentPurged`), the rating now, links to the conversation and change; the list reads only the start of the rated reply's text. Every write: row locked, only from Open (else 409 `NotOpen`, nothing written; convert with its chatbot removed: 409 `ChatbotNotFound`), its `quality_issue.<triaged|fixed|dismissed|converted>` event (actor Admin) in the same `withTenant`, relayed after the commit, answer read after it. Triage = `PATCH /:publicId` (`QualityIssueUpdate`, type and / or note, blank note = null); Mark fixed / Dismiss = `POST /:publicId/fix|dismiss` (`QualityIssueUpdate`), final (no reopen). Create test (`EvalCaseCreate`) = `POST /:publicId/test-draft` (reads in one `withTenant`, then the router outside it: the chatbot's published routing, tier Mid, `quality.test_rewrite`, `conversationId` null, budget held; the chat sent is the newest messages within `QUALITY_TEST_REWRITE_MAX_CHARS` (the answer restates them under the output cap); `QualityTestRewriteProvider` fences chat + note as data and holds the answer to `Schemas.ZQualityTestDraft`; saves nothing; failures via `QUALITY_TEST_DRAFT_FAILURE_HTTP_STATUS_MAP`) → the admin edits it in a dialog → `POST /:publicId/convert` (the reviewed draft: the chatbot's `eval_cases` row with `input` v1 / `expectations` at the current version through `Schemas.toEvalCase` (rubric only; schemaVersion inside the jsonb) + Converted with its `eval_case_id`, one `withTenant`). Chat text, notes and drafts are never logged. Pages: `/quality` and `/quality/$id` (list in 2 columns, detail card in the third at ≥1100px), tab + page in the URL (`ZQualityPageSearch`); "Flag a conversation" goes to `/conversations`. A change to open issues refreshes every view counting them through `_authenticated/-invalidation.ts` (`invalidateOpenIssueViews`, page key roots in `QUERY_KEY_ROOTS`), so pages never import each other's data layer. Runbook: `docs/runbooks/quality.md`.
- **Knowledge page (M4-7)**: `/knowledge` = Sources (`GET /dashboard/knowledge-sources`, now with each source's `name` (admin-given, `ZKnowledgeSourceName`, required on create, editable by PATCH; older rows named by the migration) and `documentCount` from one grouped count), a generic banner per Failed source, every one whatever page of the table is shown (`?status=` Failed on the sources list) ("<name> sync failed. Answers use the last good copy from <lastSyncedAt>.", no stored reason) with Retry sync, and the questions it couldn't answer. `/knowledge/$id` = one source, its actions (Sync now, Edit, Pause / Resume, Upload files, Delete) and paged documents with a title filter (remove: upload sources only); `ZKnowledgeSourcePageSearch.documentId` highlights one. Groups read only through `GET /dashboard/doc-gap-clusters` (`authorizeCompany(DocGapClusterRead)`, paged, `tab` open / answered / dismissed, every tab's count in the same answer, most-asked first) → `DocGapClustersRepo` (one `withTenant`): label, `question_count`, newest question time, the newest `DOC_GAP_SAMPLE_QUESTIONS_MAX` `question_generic` (never other `doc_gaps` text, never logged), and while Answered the document that closed it (+ its source), linked to its source's page filtered to its title with its row highlighted. Answer (`POST /:publicId/answer {documentPublicId}`) / Dismiss (`POST /:publicId/dismiss`) (`DocGapClusterUpdate`): row locked, only from Open (else 409 `NotOpen`), the document any source's of the company, read `FOR KEY SHARE` (`isForKeyShare`) so a delete of it can't commit in between (else 404), read back in the same `withTenant`, with its audit row (M4-9). "Add a document" = upload into an upload source (none → Add source on Upload; a retried answer reuses the uploaded document) or pick one (debounced title search on `…/documents?search=`, `Utility.containsPattern`), then answer. Removing a document reopens the groups it answered (`KnowledgeDocumentFilesProvider` → `reopenDocGapClustersByDocuments`, same transaction: delete, source delete, prune). The clustering that fills the groups is M5-6. Page state in the URL (`ZKnowledgePageSearch`, `ZKnowledgeSourcePageSearch`). Runbook: `docs/runbooks/knowledge.md`.
- **Tests page (M4-8)**: read only through `GET /dashboard/eval-runs` (paged, newest first, `botId`), `/summary` (the `botId` chatbot, else the default: active cases (its own + platform), the live config's gate run (`approved_by_run_id`, else its newest run), the newest Draft / Testing / Ready config's newest run, the oldest active staging connection's host), `/:publicId`, `/:publicId/cases` (paged, failed first, then safety, then name) and `/:publicId/cases/:casePublicId` (`authorizeCompany(EvalRunRead)`) → `EvalRunsRepo` (one `withTenant`). A case's result in a run only through `Schemas.evalCaseRunResult` (true = all k attempts passed, false = an attempt failed or the run ended short, null = the run is still grading it, shown as Running and left out of the safety tally); safety tallies in `EvalRunsProvider` (pure, unit-tested). `grader_output` only through `Schemas.parseEvalGraderOutput` (v1: checks of kind forbidden_tool / tool_call / readback / judge / rubric with label + detail, and an `error` that stopped grading); unreadable is shown as such. Transcript = `GET /:publicId/transcripts/:filePublicId`: a `files` row of `owner_type` `eval_result`, owned by a result of that run which points back at it (`FilesDAL.getEvalRunTranscriptFile`, else 404), ≤ `EVAL_TRANSCRIPT_MAX_BYTES` (the row's size, then the R2 object's own size before its body is read: `FileStorageProvider.getObject({ maxBytes })`), read from R2 outside the transaction, parsed by `Schemas.parseEvalTranscript` (else 422 `Unreadable`), never served raw; tool calls carry no args or values. The harness writes both shapes (M5-2 / M5-3, JSON Schema in `evals/schemas/`, Python types in `evals/diletta_evals/types/`). Cases through `/dashboard/eval-cases` (`EvalCaseRead` / `EvalCaseCreate` / `EvalCaseUpdate`) → `EvalCasesRepo`: the company's cases + every platform case (read-only, edit → 404; its conversation and rubric are never sent, `body: null`, since they gate publishing), each with its newest result (only the `botId` chatbot's runs when filtered); New case = a rubric case (`Schemas.toEvalCase`) for the `botId` chatbot, else the default; Edit / on-off locks the company's own case, merges a new conversation or rubric into the stored body read through `Schemas.readEvalCaseBody` (upgraded; another shape → 409 `NotEditable`), keeps its other checks (listed read-only under Also checks), a blank rubric only beside another check (else 409 `NothingToCheck`), a rubric that takes the expectations over the cap → 400 `TooLong` (`EVAL_CASE_UPDATE_FAILURE_HTTP_STATUS_MAP`), written at the current version only when it changed; answers read back in the same `withTenant`, with its audit row (M4-9). Runs are started by the eval harness (M5-2, `/eval/*`); the dashboard has no Run button yet. The case form is shared with Quality's Create test (`components/eval-case-form`); Quality's save refreshes the Tests case views through `invalidateTestCaseViews`. Pages: `/tests` (strip, Runs / Cases tabs, `ZTestsPageSearch`) and `/tests/$id` (cases in 2 columns, the `caseId` case's attempts in the third at ≥1100px, View transcript in a Sheet, `ZTestRunPageSearch`). Runbook: `docs/runbooks/tests.md`.
- **Audit log (M4-9)**: every dashboard and operator write records who did what on what, only through `recordAuditOrRollback(tx, …)` (`repositories/audit.ts`, over `AuditEventProvider.record`) inside the write's own `withTenant` (a critical event: `activity_log` + `event_outbox`, so rule 3.5 holds; failure → `TenantRollbackError`, so a write never commits without its row). Actor = the Repo's: Admin (`adminId` of the signed-in company admin) for dashboard Repos, Operator for operator-only ones (`ToolDefinitionsRepo`). Entity types and actions only from `Schemas.AuditEntityTypeEnum` / `AuditEntityActionEnum`, event type and dedupe key only through `auditEventType` / `auditEventDedupeKey` (a fresh ULID per call: unique, never a dedupe); a status change is its own action (Paused / Resumed / Turned on / off / Activated / Disabled), an edit Updated, both = two rows, a save that changes nothing records nothing, a refusal nothing. `detail` = `ZAuditEventDetail` (`label` only, ≤ `AUDIT_LABEL_MAX_CHARS`: a name, title or task, never chat text, values or secrets). The Repo returns `outboxIds` (`Schemas.WithOutboxIds`), which the route takes off the answer and relays with `EventOutboxRepo.relayInBackground`. A sync the platform starts has no row (`KnowledgeSourcesRepo.startSync`; the admin's is `requestSync`). Writes with their own admin event (flag, Quality page, Mark resolved) aren't recorded twice. Read only through `GET /dashboard/audit-log` (paged, newest first), `/count` and `/export` (≤ `AUDIT_LOG_EXPORT_MAX_ROWS`) (`authorizeCompany(AuditLogRead)`) → `AuditLogRepo` → `ActivityLogDAL.getAuditLog` (actor Admin or Operator only, inlined so the partial index `IDX_activity_log_company_id_created_at_audit` serves it; the admin's name joined, an operator's never read) → `AuditLogProvider` (pure, unit-tested: words + On, no internal id or detail out). Runbook: `docs/runbooks/security.md`.
- **Security page (M4-9)**: `/security` reads only through `/dashboard/security/*` (`authorizeCompany(SecurityRead)`) and the audit log routes. Identity and origins = `GET /connections` → `CompanyConnectionsRepo.getSecurityConnections` (`Schemas.SecurityConnection`: environment, issuer, origins, status and `signingKeysFetchedAt` from the JWKS cache, `JwksProvider.getCachedFetchedAt`, never a fetch; no auth settings or base URL), production first. Edit = `PUT /connections/:publicId/origins` (`ConnectionOriginsUpdate`, `ZUpdateAllowedOriginsApiRequest`: exact origins (`ZOrigin`), 1 to `ALLOWED_ORIGINS_MAX`, each once) → `updateAllowedOrigins` (whole list replaced, `updated_by` set, `OriginsChanged` audit row labelled with the environment; the same origins in any order = nothing written, the row locked first); the issuer stays operator-set. Keys = `GET /encryption-keys` (`Schemas.SecurityEncryptionKey`: version, status, created, rotated = the next version's `created_at` once not Active (never `updated_at`, which later writes move); never bytes or master key version; `isRotationInProgress` while a key is Retiring) and `POST /encryption-keys/rotate` (`EncryptionKeyRotate`) → `CompanyEncryptionKeysRepo.rotateFromDashboard`: the M1-5 rotation, now admin-only with its `Rotated` audit row (`v<n>`); the key rows locked first, so a Retiring key (or a rotation running at the same moment) → `ENCRYPTION_KEY_ROTATE_FAILURE_HTTP_STATUS_MAP` 409 `EncryptionKeyRotateFailureEnum.RotationInProgress`, nothing written (the sweep that retires it is M6-3). Prompt-injection events = `GET /injection-events` (+ `/count`, paged) → `QualityIssuesRepo.getInjectionEvents`: issues typed Prompt injection, any status (detected in = the note, else the source; action taken = `INJECTION_EVENT_ACTION_LABEL_MAP`), until M6-4 adds detections. Page state (both pages) in the URL (`ZSecurityPageSearch`); paged lists use `components/pager` (an unknown count pages by a full page, an empty page past the end shows `PastEndNote`); the audit log and injection lists are `staleTime` 0, since other pages add their rows. Runbook: `docs/runbooks/security.md`.
- **Bots page (M4-10)**: `/settings/bots` reads only through `GET /dashboard/chatbots/settings` (each chatbot with its live and open version heads and conversations over `CHATBOT_CONVERSATION_COUNT_DAYS`, `ChatbotsRepo.getChatbotSettingsRows`), `/dashboard/chatbots/:chatbotPublicId/configs` (paged, newest first, `/count`, `/:publicId`; `authorizeCompany(ChatbotConfigRead)`), `/dashboard/chatbots/config-options` (`ChatbotConfigOptionsRepo`: Active tool versions, knowledge sources, providers with an Active model key (provider column only, `getActiveModelKeyProviders`); capped at `CHATBOT_CONFIG_OPTIONS_MAX`) and `GET` / `PUT /dashboard/settings/read-only` (`ReadOnlyModeRead` / `ReadOnlyModeUpdate`, `CompaniesRepo.updateReadOnlyMode`, Turned on / off audit rows). Every call: args checked by `Schemas.validateToolArgs` (zod `fromJSONSchema`, declared properties only, at every depth) before `renderToolOp`; same tool + same args twice in a turn → `Blocked` and the turn stops (`stopWhen`). Reads: `call_op` as the user, output fenced, the turn becomes untrusted (so does a help docs search; later turns judge the transcript by what tool parts hold, never by tool name). Writes are Think `durable-pause` actions: the `approval` hook runs the read-before (none for a create: its readback reads `{result.*}`), builds the diff (`Schemas.buildChangeRequestChanges`, from the read-before and the real args, never the model's words; every arg `call_op` sends is on it), and stores tool call + change request (`encrypted_changes` = `ChangeRequestPayload`: args, read-before, diff) + `change_request.proposed` in one `withTenant`; no change → no proposal. Approval (`decideApproval`): a first-matching `blocked` rule refuses any tool; else tool `Always` / `Never` / `Policy` (config `approvalRules` × the JWT roles from `CONVERSATION_ROLES_HEADER`, counted only until that JWT's exp, first match, none = required); destructive or untrusted → always required. Required → park, `change_request` frame (also re-sent on connect), expiry schedule `CHANGE_REQUEST_APPROVAL_EXPIRY_MS` (no auto-close meanwhile), at most `CHANGE_REQUEST_MAX_PENDING` per conversation. The widget's `change_request_decision` frame decides (rate-limited; approve needs the host token from the `host_token` frame, else `token_needed`): the decision (or expiry) claims the conversation (`isDeciding`) before its first await, the database decides first (an approval after `created_at + CHANGE_REQUEST_APPROVAL_EXPIRY_MS` ends Expired), the DO follows the row's status whoever set it, then prepares the continuation like a turn and calls `approveExecution` / `rejectExecution` (Think's own storage: survives eviction; an `{status:"error"}` answer = no pause, commit directly). Commit (the action's `execute`): Approved → Committing (key `changeRequestCommitIdempotencyKey`) → Committed / Failed / NeedsHuman (`ChangeRequestErrorCodeEnum`); a refused Repo step always names its failure (a rollback = `ServerError` → entry kept, retried after `ACTION_COMMIT_RETRY_MS`); an Approved / Committing entry resumes with `isResume` only once the host token is back (`host_token` frame), never on the wake itself. Every status change = one `change_request.<action>` critical event (`Schemas.CHANGE_REQUEST_STATUS_ENTITY_ACTION_MAP`, `changeRequestEventDedupeKey`). Open change requests live in the runtime state by Think tool call id. No Workflows for commits in v1. Runbook: `docs/runbooks/actions.md`.
- **Review UI (M3-5)**: the widget shows a reply's proposals as review cards (`lib/changeRequestView.ts`, pure: grouped by reply via the view's Think `toolCallId` or the call's output `changeRequestId`, one card per tool + kind; ≤ `WIDGET_CHANGE_CARD_MAX_ROWS` records a card with Approve N / Edit / Reject, more the bulk table with a checkbox per record). Every answer goes in one `change_request_batch_decision` frame (ticked → approve, unticked → reject): the DO decides them all in the database, commits the approved ones (`runCommit`, outcome cached for `execute`), then resolves every pause back to back (`resolvePauses`) so Think continues once. Edits (`change_request_edits`) only change `Schemas.getEditableFields` (args `call_op` sends in query/body, never path args; none for a delete) and are re-checked like a new proposal (rule 3.34): `getEditPlan` → `applyChangeRequestEdits` → `validateToolArgs` → read-before again → `buildChangeRequestChanges` → refused if nothing changes → `saveEdit` (`was_edited`, `change_request.edited` event); the proposal stays Proposed with its original deadline and the user approves the re-checked diff. The widget hears each edit's outcome (`change_request_edit`). Host token (minimal): `getHostToken` init option; the widget sends `host_token` on every connect and, on `token_needed` for an answer or edit, fetches one and resends that frame once (`reason: answer`; the DO's own asks are M3-8). Runbook: `docs/runbooks/actions.md`.
- **Verify (M3-6)**: a commit the host answered 2xx is Committed, not done. `runFollowUp` (same DO step, before `execute` answers): `finishCommit` keeps the commit's response in the payload (`ChangeRequestPayload` v2: `result`, `mismatches`; v1 upgraded on read by `Schemas.parseChangeRequestPayload`) and a create's id as `host_ref` (`getChangeRequestHostRef`) → read-after (`HostToolCallProvider.readAfter`, `readback_op` with args + result, as the user) → `Schemas.checkReadAfter` (pure, shared with evals) → `finishVerify`: Matches → Verified (a delete: 404); Differs → Mismatch + what it found (`mismatches`, encrypted, frame only); Unknown → NeedsHuman `verify_unknown`, never an undo on a guess. A Mismatch is auto-undone per change request (never its batch): no `inverse_op` → NeedsHuman `not_undoable`; else undo key (`changeRequestUndoIdempotencyKey`) + `undoing` event stored first, `HostToolCallProvider.undo` (`inverse_op`, args + before + result; Emulated checked with `getUndoCheckExpectations`), read again → `finishUndo` (`undoEnd`): back as before (a create: gone) → Undone, else NeedsHuman `undo_failed` / `undo_unconfirmed`. Verify and undo don't re-check the conversation, chatbot or company (cleanup of a write that landed). No token before a send → entry kept (`verifying` / `undoing`) for the next `host_token`; an eviction resumes from the row (`startFollowUp`; a Mismatch holding the undo key resumes with `isResume`). The model hears Verified / Undone / needs review (`HostToolStatusEnum`); the widget shows Verified, Changes undone (expected vs found) and Needs a person cards (`WidgetChangeCardToneEnum`). Undo button, `undo_until` and the purge: M3-7. Runbook: `docs/runbooks/actions.md`.
- **Undo window and purge (M3-7)**: every change request that ends (Verified, Undone, Failed, Rejected, Expired) gets `undo_until` = its end + `CHANGE_REQUEST_UNDO_WINDOW_MS` (1 h, `ChangeRequestsProvider.undoUntil` in `moveStatus` / `decideChangeRequest`); NeedsHuman keeps it null (values stay until a person resolves it: Resolved sets it to now, M4-5). The user undoes a Verified one only through the widget's `change_request_undos` frame (a card's Undo: every record still inside its window): same gate as an answer (rate limit, no turn running, host token or `token_needed`), then `ActionEngineRepo.startUndo` re-checks it like a commit (conversation open, chatbot and company active, not read-only, then under the row lock `ChangeRequestsProvider.undoRefusal`: Verified with no undo under way, `inverse_op`, values not purged, before `undo_until`, and the tool still loading); a refusal changes nothing and the widget hears why (`change_request_undo`). Started = the user's own undo key (`changeRequestUserUndoIdempotencyKey`, never the auto-undo's) stored + `undoing` event by the chatbot user; it stays Verified (view `isUndoing`, DO stage `user_undoing`) and runs like the auto-undo (`runFollowUp`, which returns the undo's host outcome, `finishUndo`): Undone (view `undoneBy` from the key, which is never purged), stays Verified with an `undo_not_sent` event when nothing may have reached the host (commit key again, window kept), else NeedsHuman; its end events are the chatbot user's. Never resumed by `undo_until` + `CHANGE_REQUEST_UNDO_GRACE_MS` → the auto-close's check hands it to a person (`abandonUndo`, `undo_interrupted`). No model call: `userUndos` (summaries only, kept for the whole conversation, added from any Undone-by-user view) go into every later turn's system prompt (`HostToolsProvider.userUndoText`). The DO keeps `undoWindows` (re-sent on connect, auto-close waits for the last one); window and refusal rules are pure in `ChangeRequestsProvider` (`nextUndoWindows`, `undoRefusalReply`). Values are purged only by the per-minute `ChangeRequestPurge` cron (`ChangeRequestPurgeRepo`, `withPlatform`): `encrypted_changes`, `iv`, `encryption_key_version` null once `undo_until` has passed, sparing a Verified row holding the user's undo key until `undo_until` + the grace; `tool_calls.encrypted_args` waits for M6-1. Runbook: `docs/runbooks/actions.md`.
- **Token refresh (M3-8)**: a host call as the user that finds no token, or whose token the host refuses, goes through `ConversationDO.withFreshToken`, retried only when a second try can't write twice (nothing may have landed, or the call is a resume: the adapter reports a resume as `mayHaveLanded` even unsent, and the same plan resends it as one). The ask is `HostTokenAsk` (`src/hostToken/`, stateful per DO, unit-tested): `token_needed` `reason: refresh` to every open socket (none open = no wait), wait ≤ `HOST_TOKEN_WAIT_MS` for `host_token`, asks meanwhile share it, and an ask that timed out isn't repeated for as long (a batch waits once); then the call is tried once more, and a fresh token refused too ends the step as before. A token the host refused is dropped from memory (unless a newer one came), so the answer / edit / undo gates ask with `reason: answer`. Reads (in a turn, read-before) without one tell the model to ask the user to sign in. Commit, read-after, undo and the undo's re-read keep their entry (`waitForToken`: `tokenNeededSince` from the first wait, `isUnsent` when the first send reached nothing, passed to `startCommit` / `startFollowUp` so the resume sends fresh, cleared before every send) and resume on the next `host_token`; a wake with entries and no token asks too (`askForResumeToken`). Still waiting `HOST_TOKEN_GRACE_MS` after the first wait (widget closed) → `ActionEngineRepo.handOverForToken` (Approved / Committing / Committed / Mismatch → NeedsHuman `token_needed`), checked on the scheduled `retryCommits` and the auto-close sweep; a user undo keeps `abandonUndo`. The widget answers `refresh` silently (no UI) through `lib/hostTokenSender.ts`: one `getHostToken` at a time, a getter that throws, rejects or hangs past `WIDGET_HOST_TOKEN_FETCH_TIMEOUT_MS` never blocks the next send; `reason: answer` is the reply to its own answer / edit / undo frame. Runbook: `docs/runbooks/actions.md`.

- **Crons**: one cron trigger per Worker (`Constants.CRON_TRIGGER`, every minute, = `wrangler.jsonc` `triggers.crons`): the account's Workers Free plan allows 5 cron triggers in total, shared by every env. `scheduled()` runs the jobs `CronScheduleProvider.getDueJobs(controller.scheduledTime)` picks (pure, UTC): every minute the outbox sweep + model_calls usage backfill, hourly at `CRON_HOURLY_MINUTE` the knowledge re-sync and the activity rollups, daily at `ACTIVITY_LOG_PARTITIONS_UTC_HOUR` the partition maintenance; each through `Promise.allSettled`, so one failing never skips another.
