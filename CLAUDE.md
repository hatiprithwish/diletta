## Principles

- **Scan before code.** Read the closest golden file below before writing anything new. Mirror its naming, imports, and folder placement. No pre-existing pattern → flag it, don't assume.
- **Ambiguity halt.** Requirement unclear or conflicts with existing architecture → stop, ask one specific question. Don't guess.
- **No stubs.** No `// TODO`, placeholders, or partial features. Every delivered feature fetches, renders, errors, and empties end-to-end.
- **Multi-file features need a plan first.** Before writing code that touches >1 file, output: files to create/modify, golden file mirrored, new packages needed (if any — ask before adding), ambiguities. Wait for confirmation.
- **Ship complete.** All files in one response, fully wired — no "you'll need to connect this yourself."

## New feature checklist

1. `packages/schemas/src/<feature>/` — `<Feature>Common.ts`, `<Feature>ApiRequest.ts`, `<Feature>ApiResponse.ts`, `<Feature>DALRequest.ts`, `index.ts`; export from `packages/schemas/src/index.ts`. Add `LogCategory`/`LogAction` entries in `log.ts`. Status fields get the Status Enum Pattern (below).
2. `apps/backend/src/db/tables.ts` — add the table (see Database below), then `pnpm --filter backend db:generate` immediately, commit the migration with the schema change. Update the architecture diagram in the same PR.
3. `data-access-layer/<Feature>DAL.ts` → `repositories/<Feature>Repo.ts` → `routes/<Feature>Routes.ts`, mounted in `apps/backend/src/index.ts`.
4. `apps/web/src/routes/_authenticated/<feature>/` — `-data.ts`, `index.tsx`, `new/index.tsx` and `$id/index.tsx` if applicable, `-Component.tsx` co-located (prefixed `-`).

**Layers never skip or reverse:** Routes → Repo → DAL → DB.

## Conventions

- **Status Enum Pattern** (any discrete-state field): DB stores int only. Define `<Feature>StatusIntEnum`, `<Feature>StatusLabelEnum`, `<FEATURE>_STATUS_LABEL_MAP` in `<Feature>Common.ts`. DAL returns raw int; Repo maps int→label in a private `withStatusLabel`; API response always carries both `<feature>Status` (int) and `<feature>StatusLabel` (string). See `ChatbotsCommon.ts` / `ChatbotsRepo.ts`.
- **Public ID Pattern** (every table, except the append-only/derived `activity_log`, `event_outbox`, `activity_rollups`, `eval_results`, `knowledge_chunks`; `admins` and `chatbot_users` use `clerk_user_id` / `host_user_id`): `id` is internal-only — joins and references, never sent to or accepted from a client. `publicId` (`Utility.generatePublicId()`, unique-indexed) is client-facing — every route param, API response, and frontend reference uses it instead. DAL generates it on insert and finds rows by it; API response types structurally omit `id` and every other internal id (`companyId`, `<verb>_by`), e.g. `Omit<Chatbot, "id" | "companyId" | "createdBy" | "updatedBy">`. See `ChatbotsCommon.ts` / `ChatbotsDAL.ts` / `ChatbotsRepo.ts`.
- **DAL**: tenant DALs hold no db. Every method takes `tx` from `withTenant` first and filters on `companyId`. Non-tenant DALs (`UsersDAL`) hold `private db` from a ctor taking `env`. Every method inits `{ isSuccess: false }`, try/catch, `AppLogger.error` with `LogCategory`/`LogAction` on failure. Where: one condition `.where(eq(…))`; two or more go in a `conditions` array built before the query (optional ones via `if (x) conditions.push(…)`), then `.where(and(...conditions))`. No inline `and(…)`, no `.where(() => …)` callback (drizzle accepts it on select only).
- **Repo**: thin. Maps API shapes to DAL params; business logic lives here, not in the DAL. Tenant Repos hold `private db = getDbClient(env)` and open one `withTenant` per method.
- **Provider → DAL**: a provider in `providers/` may call a DAL directly when several Repos share the step (e.g. `CompanyKeyProvider` reads `company_encryption_keys`), or when it holds one self-contained multi-DAL step a Repo runs inside its own transaction (e.g. `CriticalEventProvider`, `ModelKeyFailureProvider`). It takes the Repo's `tx` and never opens a transaction or builds a query itself; it returns `{ isSuccess, message }` and never throws. See `providers/companyKey.ts`.
- **Encryption** (`encrypted_*` columns): only through `CompanyKeyProvider.encryptValue` / `decryptValue` (company key create/rotate: `CompanyKeyProvider.createCompanyKey`, `CompanyEncryptionKeysRepo`), which use `@app/crypto`. Store `encryption_key_version` and `iv` with the ciphertext and decrypt with the row's version. Plaintext is encrypted in the Repo before the DAL; it never reaches a DAL param, a log or a route response (`getDecrypted*` responses are server-side only). Ciphertext, iv and key bytes stay out of log metadata.
- **Pagination** (any list that grows without bound): request extends `ZPageApiRequest` (`common.ts`) with a `<Feature>SortColumn` enum; Repo fills defaults (`Constants.DEFAULT_PAGE_NO`/`DEFAULT_PAGE_SIZE`, `createdAt` desc); DAL maps the sort column, then `.orderBy(expr, asc(<table>.id)).limit(pageSize).offset((pageNo - 1) * pageSize)`. Totals come from a separate `get<Feature>Count` returning `TotalRecordsResponse`. No cursors. See `ChatbotUsersDAL.ts`.
- **Routes**: `checkAuth` → `authorizeCompany(action)` (`/dashboard/*`) or `authorizePlatform(action)` (`/operator/*`) → `zValidator` → handler. Authorizing before validating means an unauthorized call gets 403, not 400. `c.get("companyId")` is the tenant key (from the signed-in admin, never the client). 201/200/403/404/500: a DAL not-found path sets `isNotFound: true` (with `isSuccess: false`), and the route answers `isSuccess ? 200 : isNotFound ? 404 : 500`, so a server error never shows as 404. Only `GET /dashboard/me` runs without an authorize middleware.
- **Authz (M1-8)**: one `can(admin, action, resource)` (`packages/schemas/src/authz/`) for every dashboard and operator action. A new action goes in `AuthzActionEnum` (and in `OPERATOR_ONLY_ACTIONS` if a company admin must never perform it). Roles are derived from `admins.company_id`: NULL = operator, set = company admin. No role column. Company admins are created on first sign-in from Clerk invite metadata (`companyPublicId`), which is consumed in the same transaction so a deleted row stays deleted; operators are added by hand only (`docs/runbooks/operators.md`). Never create an `admins` row with no company from code. Admins of a churned company have no access (`AdminsRepo.resolveAdmin`); paused keeps access.
- **Widget auth (M2-1, ADR 0001)**: `GET /widget/ws` takes the companion JWT in `Sec-WebSocket-Protocol` (`['diletta.v1', <jwt>]`), never in the URL, and decides everything before the upgrade. Only `WidgetAuthRepo.authenticate` turns it into a `WidgetIdentity` (server-side, internal ids): alg allowlist RS256/ES256 + `kid`, no `crit` → issuer → `company_connections` (`withPlatform`) → signature on the issuer's JWKS (`JwksProvider`, KV `JWKS_CACHE`, fetched only for a registered issuer, size-capped) → `aud = WIDGET_JWT_AUDIENCE`, `exp`/`nbf`/`iat`, lifetime ≤ 5 min → connection active + `Origin` in `allowed_origins` → active company and chatbot (`withTenant`). Every failure before the signature passes is 401, so only a signed token can see 403/404. Failures are HTTP statuses (`WIDGET_AUTH_FAILURE_HTTP_STATUS_MAP`) with a generic body; the answer selects `diletta.v1` only. `GET /widget/bootstrap` (M2-7, ADR 0002) takes the same token as `Authorization: Bearer` (scheme in any case) through the same `authenticate`, reads only (`WidgetBootstrapRepo`: chatbot name + published config's `widget` block, `widget: null` without one) and creates nothing; `/widget/*` sets its own CORS (any origin, no credentials, only `Authorization`), the data gated by `allowed_origins`. Both routes validate their query only after `authenticate`, so no valid token = 401 whatever the query.
- **Conversation DO (M2-2)**: `ConversationsRepo.startOrResume` (worker, after auth) upserts the `chatbot_users` row and creates the conversation (with a `conversation.started` critical event as `root_log_id`) or resumes the user's own open one (else `ConversationStartFailureEnum.NotFound` → 404). The worker then forwards the upgrade to `ConversationDO` (`getAgentByName`, name = `conversations.public_id`) with a fresh header set carrying the session (`CONVERSATION_SESSION_HEADER`), and closes a conversation it just created if that upgrade fails; the DO has no public route. The DO extends Think, locked down: no workspace bash or MCP, its tools are `search_help_docs` (M2-6; active only when the bot lists knowledge sources) and the config's pinned host tools (M3-4), no reasoning or identity frames, `onChatError` returns safe text only. Every inbound frame passes `WidgetFrameProvider.admit` (pure, unit-tested): a chat request is rebuilt to its newest user message with a new id; cancel and stream resume pass; the widget's own `feedback` frame (M2-7) is stored by the DO (read model synced first, then `FeedbackRepo.recordFeedback` on a synced reply of this conversation, one row per reply per user, answered `{type:"feedback", rating | null}`; `recordFeedback` re-checks the conversation open and the company and chatbot active, refused while closing, at most `FEEDBACK_FRAMES_PER_WINDOW` per conversation per minute, stored one at a time in arrival order); everything else is refused. The `conversation` frame carries the ratings already given (the newest `CONVERSATION_FEEDBACK_MAX_RATINGS` replies', each entry parsed on its own), which the worker reads before the upgrade (`CONVERSATION_FEEDBACK_HEADER`), so connecting costs the DO no database read (except to resend open change requests, M3-4). One turn at a time, refused while closing; the turn's ULID (`Utility.generateUlid`) and the activity time are stored at admission, then `loadTurnConfig` re-checks the conversation, chatbot and company and loads the published config (so a publish or a pause takes effect at the next message) and the model is routed; any failure → `{type:"unavailable"}` (or `closed`), nothing saved. `webSocketMessage` initializes the DO (`__unsafe_ensureInitialized`) before checking a frame, so after a hibernation wake the reused-id check sees the stored transcript. The read model is synced from the transcript (`TranscriptProvider`, position = the last synced message id, never an index) after every turn and, in `waitUntil`, on every wake, so a failed write or an evicted turn is caught up; `recordTurn` is idempotent on `session_message_id`. A conversation never closes over an unsynced backlog. A turn Think ends without a hook is released in a `finally` around the frame's dispatch. Auto-close after `CONVERSATION_IDLE_CLOSE_MS` (DO schedule, never sooner than `CONVERSATION_CLOSE_RETRY_MS` from now): Closed, Answered or Abandoned. DO runtime state goes through `patchRuntimeState` (no await between read and write).
- **Widget UI (M2-7)**: `apps/widget`, one store per widget (`createWidgetStore`), never a module singleton. Hooks turn Think's transcript and the DO's frames into `Schemas.WidgetPanelView`; components only render it (the dev gallery `?gallery` draws every state from sample data). Every DO frame is parsed with `ZWidgetServerMessage`, every tool output with its schema, before use. The socket opens only for a first message or a saved conversation (never on page load); a new conversation id is saved and the session remounted with it (`ChatSession` keyed by id) before anything is sent; a saved conversation the server keeps refusing is dropped and the widget goes idle (`lib/connectFailures.ts`; a failed `getToken` counts but never drops it). `getToken` is called for every connect and every bootstrap read, the token never stored; each token tells the store the host user (SHA-256 of `sub`, `lib/hostUser.ts`), which keys the saved id. `DilettaWidget` gets a fresh store per apiBase + chatbot; the script tag's controllers act only on their own widget. Widget types and props live in `WidgetUi.ts`; sizes off the preset scale are `@theme` tokens in `widget.css` (`text-widget-*`, `rounded-widget-*`), kept out of `cn()` next to a text colour. Markdown is the widget's own safe parser (`lib/markdown.ts`: no HTML, links only http(s)/mailto). Review cards (M3-5) render `Schemas.WidgetChangeCardView` only; their actions live in `hooks/useChangeReview.ts`. Styles go into the shadow root through `prepareShadowCss` (`:root` → `:host`, rem → px, `@property` hoisted); the host document gets only the `@property` rules and the fonts link. The script-tag bundle stays under `WIDGET_BUNDLE_MAX_GZIP_BYTES` (the build fails above it). Runbook: `docs/runbooks/widget.md`.
- **Frontend `-data.ts`**: `Queries` class with hierarchical keys (`keys.all()` invalidates every detail) and `queryOptions` builders; the hooks (`useX`) are plain exported functions next to it (rules of hooks forbid them in a class). `setQueryData` on update, `removeQueries` on delete, `mutateAsync` when the caller must await, `mutate` otherwise. Every mutation needs a non-empty `onError` (toast).
- **Frontend pages**: `useAuth()` at page level, explicit loading/error states, all requests through `apiClient`.

## Database

**Neon Postgres via Hyperdrive (Drizzle `node-postgres`, Hyperdrive caching disabled):**

- `pgTable` aliased `table`; camelCase in code, `snake_case` in DB. Unique-index `publicId` and any other unique field.
- ids: `t.bigint({ mode: "string" }).primaryKey().generatedAlwaysAsIdentity()` (string in code, exact int64), internal only; `publicId` everywhere else.
- `created_at` and `updated_at`: `t.timestamp(..., { withTimezone: true }).notNull().defaultNow()` (append-only/derived tables above: no `updated_at`). DAL sets `updatedAt` on update. Status/type ints: `t.smallint()`.
- No DB foreign keys: the DAL checks references. Index every reference column.
- `halfvec` columns and HNSW indexes go in `tables.ts` (`t.halfvec("embedding", { dimensions: 1024 })`, `.using("hnsw", col.op("halfvec_cosine_ops"))`). RLS policies, partitions and extensions live in custom SQL migrations (`pnpm --filter backend db:generate:sql <name>`) in the same `src/db/migrations` journal as drizzle-kit output, so ordering is guaranteed.
- `activity_log` is partitioned by month (`*_partition_activity_log` migration), so its primary key is `(id, created_at)`. A daily Cron (`ActivityLogPartitionsCron` → `ActivityLogPartitionsRepo`) keeps the current UTC month and the next 3 partitioned, and alerts if a month is missing or `activity_log_default` holds rows (it must stay empty). Runbook: `docs/runbooks/activity-log-partitions.md`.
- `diletta_app` never gets DDL rights. Where the worker needs an owner action, it calls a `SECURITY DEFINER` function owned by the owner role that does one fixed thing, validates its arguments, sets `search_path = pg_catalog, public, pg_temp`, and is `REVOKE`d from `PUBLIC` and granted `EXECUTE` to `diletta_app` only. See `*_activity_log_partition_maintenance`.
- Every new migration folder gets a hand-written `down.sql` that reverses it (`--> statement-breakpoint` between statements). `db:rollback` runs it and removes the journal row.
- `dbClient.ts` builds a client per request from `env.HYPERDRIVE.connectionString`; never cache a client across requests.
- Environments: staging and production only. Two Neon branches (`staging`, `production`), each behind its own Hyperdrive config. Local dev and tests use the staging branch via `apps/backend/.env`; never point local at production. Tests must clean up the rows they create.
- Roles: the worker (Hyperdrive, and `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` locally) connects as `diletta_app`, which RLS applies to. The owner role (`DATABASE_URL`, `BYPASSRLS`) runs migrations and test fixtures/cleanup only, never code under test. Setup and password rotation: `docs/runbooks/app-role.md`.

**From M0-5 (tenant pattern):**

- Tenant queries only inside `withTenant(db, companyId, tx => ...)` (`companyId` = internal `companies.id`, resolved server-side), which sets `set_config('app.company_id', …, true)` per transaction. Never set RLS context per session. DAL methods take `tx`; Repo opens the transaction.
- Only exception: a backend test may set `app.company_id` per session (`set_config(…, false)`) as a leak-detection control, on a direct single-connection pool (never `NEON_POOLER_URL`), with `RESET app.company_id` in a `finally`. See pattern rule 3.2 and `withTenant.test.ts`.
- Transactional flows (outbox, action engine) throw `TenantRollbackError(dalResponse.message)` to roll back; `withTenant` turns it into `{ isSuccess: false, message }`. Plain CRUD keeps the `{ isSuccess }` response pattern. See `ChatbotsRepo.setDefaultChatbot`.
- Critical events: `activity_log` + `event_outbox` row in the same transaction, only through `CriticalEventProvider.record(tx, …)` inside the Repo's `withTenant` (`EventOutboxRepo.recordCriticalEvent` when the event is the only write). The caller derives a `dedupeKey`; a repeat, concurrent or not, is a no-op success (the provider holds a transaction-scoped lock on the key, so a concurrent repeat waits for the first commit). After commit, relay with `ctx.waitUntil(EventOutboxRepo.relayEvents({ companyId, outboxIds }))`; the per-minute Cron sweep publishes what that misses. Delivery is at-least-once: Queue consumers dedupe on `outboxId`, ack per message, go through a Repo. See `providers/criticalEvent.ts` / `EventOutboxRepo.ts`.
- Cross-company work (operator routes, Cron/Queue sweeps across companies, and the Clerk admin → company and JWT issuer → connection lookups) runs in `withPlatform(db, tx => ...)`, which sets `app.is_platform` per transaction and passes every policy. Anything scoped to one company uses `withTenant`, even for an operator.
- **RLS (M1-3):** every tenant table and `companies` has RLS enabled and forced, with a tenant and a platform policy; `admins` with no company (operators) and platform `eval_cases` never match a tenant, and tenants may read platform cases but not write them. The DAL still filters on `companyId` on top of RLS.
- A new table ships, in the same PR, a custom migration that grants it to `diletta_app` by name (no default privileges) and, for a tenant table, enables and forces RLS with both policies, mirroring `*_rls_policies`. A new tenant table also gets a `FIXTURES` entry in `rls.test.ts`, and new tenant Repo methods get cross-company tests run as `diletta_app`.

## Runtime

- Model calls only through the model router, on the company's own key via AI Gateway. No direct provider SDK calls.
- **Model router (M2-3)**: `ModelRouterRepo.getModel({ companyId, chatbotId, chatbotUserId, conversationId, evalRunId, turnId, taskType, tier, routing })` → `{ isSuccess: true, model } | { isSuccess: false, failure }`, never throws. Steps: tier (or `routing.defaultTier`) → provider + model; must be in `MODEL_PRICES` (`packages/schemas/src/modelRouter/`), else `ModelNotPriced`; active key decrypted in `withTenant` (`CompanyKeyProvider.decryptCompanySecret`); `AiGatewayProvider` (the only file that imports `@ai-sdk/*`) builds the provider-native model on AI Gateway with the key, `cf-aig-authorization` and `cf-aig-metadata`, wrapped by `ModelCallRecordingProvider`. That middleware holds every usage-status rule (Reported: provider usage, or a refusal with status ≥ 400 at 0; Pending: billed but no usage, incl. a finish without totals or an unreadable 2xx, backfilled by the per-minute Cron from the gateway log; Unknown: no log id) and turns every final failure into `ModelUnavailableError` (text `MODEL_UNAVAILABLE_MESSAGE`; an abort stays an abort), because Think sends a stream error's message to the widget as is. It also does the retrying (a retryable 408/409/429/5xx, up to `MODEL_CALL_MAX_RETRIES`, honouring retry-after and abort), since the SDK only retries its own errors; a gateway 5xx/408 counts as possibly billed (Pending), not refused. `ModelCallsRepo.recordModelCall` writes the row in `ctx.waitUntil`. Key failure = no active key, or the provider's own 401 / Google `API_KEY_INVALID` (never a 403, never a gateway error) → `ModelKeyFailureProvider` in the Repo's tx: key Invalid only if it still holds the value used (`invalidateModelKey`), and the company's one open System / ModelError issue covers the provider (which providers it covers is read from its `quality_issue.opened` / `provider_added` events, never the note). Never write a billed call as $0 Reported. A price change or new model = edit `MODEL_PRICES` with its source date. Setup and backfill: `docs/runbooks/ai-gateway.md`.
- **Budget (M2-4)**: every provider call is sized and held before it goes out, and a refused call never reaches the provider (pattern rule 3.24). `ModelCallRecordingProvider` estimates the prompt once per call and, per attempt (retries too), asks `budget.reserve` for a hold, then sends the attempt with the hold's `maxOutputTokens` straight to the wrapped model. `ModelCallBudgetProvider` (the router's only budget code) sizes it: input at the plain input rate, output ≤ `MODEL_CALL_MAX_OUTPUT_TOKENS`, cut to the caller's output tokens and cost left (a pricey model gets a shorter answer, not a refusal), refused under `MODEL_CALL_MIN_OUTPUT_TOKENS`; holds it in `GetModelRequest.caps` then `BudgetDO.reserve`; settles each record against its own hold (unknown usage keeps the whole cost hold but counts no output tokens). `ModelCallCaps` is the Conversation DO's `TurnBudget` (`src/budget/`, stateful per turn, so not in `providers/`): `maxTokensPerTurn` counts **output only**, plus `turnCostCapUsd` / `conversationCostCapUsd`. `BudgetDO` is one per company (reach it only via `BudgetDO.forCompany`; plain `DurableObject`, SQLite kv, micro-dollars via `usdToMicros`): every RPC request is Zod-parsed; billing period = UTC month, seeded from `SUM(model_calls.cost_usd)` through `BudgetRepo`; `spending_budget` re-read every `BUDGET_REFRESH_MS` (NULL = `DEFAULT_SPENDING_BUDGET_USD`, $10), a failed read retried after `BUDGET_LOAD_RETRY_MS`; chatbot-user daily cost and messages per minute live there too. Its math is pure in `BudgetLedgerProvider`; expired holds are charged before the ledger is read for a check, with no await between reading and writing; it fails closed (`Unavailable`). The Conversation DO checks `conversationTurnsPerHour` and `conversationCostCapUsd` before routing and `BudgetDO.admitTurn` after it (so a turn that can't run uses no rate slot); a rate refusal answers `BUDGET_RATE_LIMIT_MESSAGE`, any other `unavailable`, nothing saved. `beforeTurn` sets `stopWhen` (caps used up) and `timeout.totalMs` (`turnTimeoutSeconds`). Runbook: `docs/runbooks/budget.md`; its Known gaps list what isn't built yet (50/80/100% alerts, the tool loop guard) and where the count is knowingly off.
- **Knowledge ingestion (M2-5)**: sources → documents → chunks. A sync starts only through `KnowledgeSourcesRepo.startSync` (create of a web source, `POST /dashboard/knowledge-sources/:id/sync`, an upload or an upload source's resume, the hourly `KnowledgeResyncCron` for due Daily / Weekly sources, Failed ones after `KNOWLEDGE_FAILED_RETRY_MS`, and stale syncs): the source row is locked `FOR UPDATE` and claimed (Syncing + a new `sync_run_id` = the workflow instance id; refused while Paused or while its heartbeat is fresh), then `KnowledgeSyncWorkflowProvider` starts that instance (a failed start → Failed). Only the run whose id the source holds may write: every step locks the source, checks Syncing + `sync_run_id`, and refreshes `sync_heartbeat_at`; anything else answers Stopped and writes nothing (pause, delete and a newer claim take the same lock). Steps call `KnowledgeIngestionRepo`, return ids/outcomes only, and throw on a database failure so Workflows retries them. List (sitemap pages on the source's site, `www.` = apex, default port; `isComplete` false when a nested sitemap failed or a cap hit; a url; or an upload source's documents with work to do) → per item: fetch (`KnowledgeFetchProvider`: every redirect hop re-checked against the site, time/size caps) or read from R2 → `AI.toMarkdown` (`KnowledgeExtractProvider`; md/txt decoded by BOM/charset) → normalize (NUL dropped) → `content_hash` = `KNOWLEDGE_PIPELINE_VERSION:` + sha256 of the text. Indexed + same hash = Unchanged: no chunking, zero embed calls. Prune only after a complete, non-empty listing. Finish → Active / Failed, plus a follow-up sync if uploads are still Pending. Bump `KNOWLEDGE_PIPELINE_VERSION` when the chunker or embedding model changes. Tests never reach Workers AI (`remoteBindings: false`; mock the knowledge providers). Runbook: `docs/runbooks/knowledge.md`.
- **Knowledge search (M2-6)**: the model searches through the `search_help_docs` tool (`ConversationDO.getTools`); `beforeTurn` activates it and adds `SearchHelpDocsProvider.instructions` only when the turn's config lists sources. `KnowledgeSearchRepo.search` (never throws): the bot's `knowledge.sourceIds` (public ids) → internal ids that exist in the company, any status (Paused stops syncing, not search); none left or a blank query = no hits, no model call. Then embed the query (`KnowledgeEmbedProvider`, `search.embed`) → one `withTenant` with `hnsw.iterative_scan = relaxed_order` + `hnsw.ef_search` set per transaction: vector side (HNSW cosine) and keyword side (`websearch_to_tsquery` on the GIN `tsv`), each `KNOWLEDGE_SEARCH_CANDIDATES_PER_SIDE`, only Indexed documents and `embedding_model = KNOWLEDGE_EMBEDDING_MODEL` → RRF (`KnowledgeRankingProvider`, k = `KNOWLEDGE_SEARCH_RRF_K`) to `KNOWLEDGE_SEARCH_RERANK_CANDIDATES` → rerank (`KnowledgeRerankProvider`, bge-reranker-base, `search.rerank`; Workers AI returns probabilities in 0–1, used as they are, anything outside refused) → hits ≥ `KNOWLEDGE_SEARCH_MIN_SCORE`, at most `topK`. - **Tool definitions (M3-1)**: operator-curated (`/operator/companies/:companyPublicId/tool-definitions`: `authorizePlatform(ToolDefinition*)` → `resolveOperatorCompany()` (company by public id in `withPlatform`, unknown → 404) → `withTenant` on it). Ops (`input_schema`, `call_op` `{method, path, query?, bodyMap?}`, `readback_op` `{GET, path, query?, compare}` (writes only; compare key = arg name, value = dot path into the readback response), `inverse_op` (null = not undoable)) are one unit at `tool_definitions.schema_version`: written only through `normalizeToolOps`, read only through `loadToolOps` (`ToolOpsRegistry`, rule 3.12), risk checked with `getToolRiskOpsIssue`. Placeholders `{args.*}` (must be an `input_schema` property; call_op reads args only, readback_op args + result, inverse_op args + before + result) are filled only by `renderToolOp`: a whole-string placeholder keeps its JSON type, embedded ones are text (URL-encoded in the path; an empty path value, an empty segment or a `.`/`..` segment is refused), a query/body value that is exactly one `{args.*}` placeholder with no value drops its key (in the query a `null` arg too), a `{args|before|result…}` token that isn't a full placeholder is refused on write, any other missing value fails; it never throws. Whether an arg is required is not the renderer's job: the model's args are checked against `input_schema` before rendering (M3-4). Lifecycle: create = v1 Draft (a used name is refused, 409 `NameTaken`: use `POST /:publicId/versions`); edit/delete Draft only (the DAL matches Draft rows); new version copies into a Draft at highest + 1, one Draft per name (advisory lock on company + name); Draft → Active, Active ↔ Disabled, activation re-checks ops, risk and connection; the connection must be Active, REST, have a `base_url` and auth settings with an AuthStrategy (`getAuthConfigIssue`) (create, connection change, activation; else 400 `ConnectionUnavailable`). Failure → HTTP status only via `TOOL_DEFINITION_FAILURE_HTTP_STATUS_MAP`. Several versions of a name may be Active at once (live config on v1, draft and its gate eval on v2, rollback back to v1); activating never disables another, and the runtime loads exactly the config's `{name, version}` pins, never by name. Tool name: provider rules, `search_help_docs` reserved. An `input_schema` the runtime can't check (`getToolInputSchemaIssue`) is refused on save and activation.
- **Host adapter (M3-2)**: every host API call goes through `@app/adapter` (`RestAdapter.create({ connection, getHostToken, fetch?, wait? })` → `execute` (`call_op`, tagged with the tool's risk) / `readback` (GET only) / `undo` (`inverse_op`)); nothing else calls a host with `fetch`. It takes requests from `renderToolOp` only, returns `HostCallResponse` (`HostCallOutcomeEnum`, `mayHaveLanded` for writes), never throws, and its messages hold no token, body or args. The connection is checked once at create (REST, https `base_url` with no query or credentials, auth settings). URL = `base_url` + path, refused if it would leave `base_url` (origin and path, incl. an encoded `.` / `..`); redirects never followed; per-attempt timeout `HOST_CALL_TIMEOUT_MS` and response cap `HOST_RESPONSE_MAX_BYTES`; `Retry-After` is whole seconds or an HTTP date only. Auth: `AUTH_STRATEGIES` in `@app/adapter` matches `Schemas.SUPPORTED_AUTH_TYPES` (`auth_config` schema + credential scopes per type; a test checks both); v1 = `jwt_forward` only (`{}` config, scope None, `Authorization: Bearer` from DO memory, read per attempt; none → `TokenNeeded`, malformed or 401 → `TokenRejected`). A connection whose auth settings fail `getAuthConfigIssue` is refused on create, on an `auth_config` update (checked against the stored auth type), and for every tool definition save or activation; a row saved before M3-2 with an unbuilt auth type takes no `auth_config` update and serves no tool: replace it with a new connection. Retries (at most `HOST_CALL_MAX_RETRIES`, Retry-After capped): reads 408 / 429 / 5xx / no answer. Writes: a 429 is always resent; anything else that may have landed follows `idempotency_mode`. Native resends (409 too) with the same `Idempotency-Key`. Emulated reads back first, on the last try too (`appliedCheck`: `readback_op` + `getCommitCheckExpectations` / `getUndoCheckExpectations`, `compareReadback`): shows the step's values → `AlreadyApplied`; still shows the values it replaces → resend (on the last try `Failed`); unreadable, nothing to compare, or neither (a value the host stores in another form) → `Unknown`, never resent. None → `Unknown`. A 3xx on a write is `Unknown`. `isResume` (an earlier call may have landed): Native resends with the same key, Emulated checks first, None returns `Unknown` unsent. An Emulated write tool's `readback_op` and `inverse_op` never read `{result.*}` (`getToolRiskOpsIssue`, on every write and activation). Refused / Failed never follow a send that may have landed (they become `Unknown`), but `TokenNeeded` / `TokenRejected` can, so the token can be refreshed: the caller (M3-4) reads `mayHaveLanded` on every non-success outcome, persists it, and passes it as `isResume` on the next call for the step. It owns the key per step (commit and undo differ).
- **Action engine (M3-4)**: `ConversationDO` + `ActionEngineRepo` + `HostToolCallProvider` (the backend's only `@app/adapter` caller) + `HostToolsProvider` (pure: approval, loop key, untrusted history, `<host_data>` fence). Turn start: `loadTurnTools` loads the config's exact pins; a pin not Active, on a connection that can't serve calls, with ops that don't load or an `input_schema` that can't be checked is left out (logged); a read-only company (`is_read_only`) gets read tools only. Every call: args checked by `Schemas.validateToolArgs` (zod `fromJSONSchema`, declared properties only, at every depth) before `renderToolOp`; same tool + same args twice in a turn → `Blocked` and the turn stops (`stopWhen`). Reads: `call_op` as the user, output fenced, the turn becomes untrusted (so does a help docs search; later turns judge the transcript by what tool parts hold, never by tool name). Writes are Think `durable-pause` actions: the `approval` hook runs the read-before (none for a create: its readback reads `{result.*}`), builds the diff (`Schemas.buildChangeRequestChanges`, from the read-before and the real args, never the model's words; every arg `call_op` sends is on it), and stores tool call + change request (`encrypted_changes` = `ChangeRequestPayload`: args, read-before, diff) + `change_request.proposed` in one `withTenant`; no change → no proposal. Approval (`decideApproval`): a first-matching `blocked` rule refuses any tool; else tool `Always` / `Never` / `Policy` (config `approvalRules` × the JWT roles from `CONVERSATION_ROLES_HEADER`, counted only until that JWT's exp, first match, none = required); destructive or untrusted → always required. Required → park, `change_request` frame (also re-sent on connect), expiry schedule `CHANGE_REQUEST_APPROVAL_EXPIRY_MS` (no auto-close meanwhile), at most `CHANGE_REQUEST_MAX_PENDING` per conversation. The widget's `change_request_decision` frame decides (rate-limited; approve needs the host token from the `host_token` frame, else `token_needed`): the decision (or expiry) claims the conversation (`isDeciding`) before its first await, the database decides first (an approval after `created_at + CHANGE_REQUEST_APPROVAL_EXPIRY_MS` ends Expired), the DO follows the row's status whoever set it, then prepares the continuation like a turn and calls `approveExecution` / `rejectExecution` (Think's own storage: survives eviction; an `{status:"error"}` answer = no pause, commit directly). Commit (the action's `execute`): Approved → Committing (key `changeRequestCommitIdempotencyKey`) → Committed / Failed / NeedsHuman (`ChangeRequestErrorCodeEnum`); a refused Repo step always names its failure (a rollback = `ServerError` → entry kept, retried after `ACTION_COMMIT_RETRY_MS`); an Approved / Committing entry resumes with `isResume` only once the host token is back (`host_token` frame), never on the wake itself. Every status change = one `change_request.<action>` critical event (`Schemas.CHANGE_REQUEST_STATUS_ENTITY_ACTION_MAP`, `changeRequestEventDedupeKey`). Open change requests live in the runtime state by Think tool call id. No Workflows for commits in v1. Runbook: `docs/runbooks/actions.md`.
- **Review UI (M3-5)**: the widget shows a reply's proposals as review cards (`lib/changeRequestView.ts`, pure: grouped by reply via the view's Think `toolCallId` or the call's output `changeRequestId`, one card per tool + kind; ≤ `WIDGET_CHANGE_CARD_MAX_ROWS` records a card with Approve N / Edit / Reject, more the bulk table with a checkbox per record). Every answer goes in one `change_request_batch_decision` frame (ticked → approve, unticked → reject): the DO decides them all in the database, commits the approved ones (`runCommit`, outcome cached for `execute`), then resolves every pause back to back (`resolvePauses`) so Think continues once. Edits (`change_request_edits`) only change `Schemas.getEditableFields` (args `call_op` sends in query/body, never path args; none for a delete) and are re-checked like a new proposal (rule 3.34): `getEditPlan` → `applyChangeRequestEdits` → `validateToolArgs` → read-before again → `buildChangeRequestChanges` → refused if nothing changes → `saveEdit` (`was_edited`, `change_request.edited` event); the proposal stays Proposed with its original deadline and the user approves the re-checked diff. The widget hears each edit's outcome (`change_request_edit`). Host token (minimal): `getHostToken` init option; the widget sends `host_token` on every connect and, on `token_needed` for an answer or edit, fetches one and resends that frame once (`reason: answer`; the DO's own asks are M3-8). Runbook: `docs/runbooks/actions.md`.
- **Verify (M3-6)**: a commit the host answered 2xx is Committed, not done. `runFollowUp` (same DO step, before `execute` answers): `finishCommit` keeps the commit's response in the payload (`ChangeRequestPayload` v2: `result`, `mismatches`; v1 upgraded on read by `Schemas.parseChangeRequestPayload`) and a create's id as `host_ref` (`getChangeRequestHostRef`) → read-after (`HostToolCallProvider.readAfter`, `readback_op` with args + result, as the user) → `Schemas.checkReadAfter` (pure, shared with evals) → `finishVerify`: Matches → Verified (a delete: 404); Differs → Mismatch + what it found (`mismatches`, encrypted, frame only); Unknown → NeedsHuman `verify_unknown`, never an undo on a guess. A Mismatch is auto-undone per change request (never its batch): no `inverse_op` → NeedsHuman `not_undoable`; else undo key (`changeRequestUndoIdempotencyKey`) + `undoing` event stored first, `HostToolCallProvider.undo` (`inverse_op`, args + before + result; Emulated checked with `getUndoCheckExpectations`), read again → `finishUndo` (`undoEnd`): back as before (a create: gone) → Undone, else NeedsHuman `undo_failed` / `undo_unconfirmed`. Verify and undo don't re-check the conversation, chatbot or company (cleanup of a write that landed). No token before a send → entry kept (`verifying` / `undoing`) for the next `host_token`; an eviction resumes from the row (`startFollowUp`; a Mismatch holding the undo key resumes with `isResume`). The model hears Verified / Undone / needs review (`HostToolStatusEnum`); the widget shows Verified, Changes undone (expected vs found) and Needs a person cards (`WidgetChangeCardToneEnum`). Undo button, `undo_until` and the purge: M3-7. Runbook: `docs/runbooks/actions.md`.
- **Undo window and purge (M3-7)**: every change request that ends (Verified, Undone, Failed, Rejected, Expired) gets `undo_until` = its end + `CHANGE_REQUEST_UNDO_WINDOW_MS` (1 h, `ChangeRequestsProvider.undoUntil` in `moveStatus` / `decideChangeRequest`); NeedsHuman keeps it null (values stay until a person resolves it: Resolved sets it to now, M4-5). The user undoes a Verified one only through the widget's `change_request_undos` frame (a card's Undo: every record still inside its window): same gate as an answer (rate limit, no turn running, host token or `token_needed`), then `ActionEngineRepo.startUndo` re-checks it like a commit (conversation open, chatbot and company active, not read-only, then under the row lock `ChangeRequestsProvider.undoRefusal`: Verified with no undo under way, `inverse_op`, values not purged, before `undo_until`, and the tool still loading); a refusal changes nothing and the widget hears why (`change_request_undo`). Started = the user's own undo key (`changeRequestUserUndoIdempotencyKey`, never the auto-undo's) stored + `undoing` event by the chatbot user; it stays Verified (view `isUndoing`, DO stage `user_undoing`) and runs like the auto-undo (`runFollowUp`, which returns the undo's host outcome, `finishUndo`): Undone (view `undoneBy` from the key, which is never purged), stays Verified with an `undo_not_sent` event when nothing may have reached the host (commit key again, window kept), else NeedsHuman; its end events are the chatbot user's. Never resumed by `undo_until` + `CHANGE_REQUEST_UNDO_GRACE_MS` → the auto-close's check hands it to a person (`abandonUndo`, `undo_interrupted`). No model call: `userUndos` (summaries only, kept for the whole conversation, added from any Undone-by-user view) go into every later turn's system prompt (`HostToolsProvider.userUndoText`). The DO keeps `undoWindows` (re-sent on connect, auto-close waits for the last one); window and refusal rules are pure in `ChangeRequestsProvider` (`nextUndoWindows`, `undoRefusalReply`). Values are purged only by the per-minute `ChangeRequestPurge` cron (`ChangeRequestPurgeRepo`, `withPlatform`): `encrypted_changes`, `iv`, `encryption_key_version` null once `undo_until` has passed, sparing a Verified row holding the user's undo key until `undo_until` + the grace; `tool_calls.encrypted_args` waits for M6-1. Runbook: `docs/runbooks/actions.md`.
- **Token refresh (M3-8)**: a host call as the user that finds no token, or whose token the host refuses, goes through `ConversationDO.withFreshToken`, retried only when a second try can't write twice (nothing may have landed, or the call is a resume: the adapter reports a resume as `mayHaveLanded` even unsent, and the same plan resends it as one). The ask is `HostTokenAsk` (`src/hostToken/`, stateful per DO, unit-tested): `token_needed` `reason: refresh` to every open socket (none open = no wait), wait ≤ `HOST_TOKEN_WAIT_MS` for `host_token`, asks meanwhile share it, and an ask that timed out isn't repeated for as long (a batch waits once); then the call is tried once more, and a fresh token refused too ends the step as before. A token the host refused is dropped from memory (unless a newer one came), so the answer / edit / undo gates ask with `reason: answer`. Reads (in a turn, read-before) without one tell the model to ask the user to sign in. Commit, read-after, undo and the undo's re-read keep their entry (`waitForToken`: `tokenNeededSince` from the first wait, `isUnsent` when the first send reached nothing, passed to `startCommit` / `startFollowUp` so the resume sends fresh, cleared before every send) and resume on the next `host_token`; a wake with entries and no token asks too (`askForResumeToken`). Still waiting `HOST_TOKEN_GRACE_MS` after the first wait (widget closed) → `ActionEngineRepo.handOverForToken` (Approved / Committing / Committed / Mismatch → NeedsHuman `token_needed`), checked on the scheduled `retryCommits` and the auto-close sweep; a user undo keeps `abandonUndo`. The widget answers `refresh` silently (no UI) through `lib/hostTokenSender.ts`: one `getHostToken` at a time, a getter that throws, rejects or hangs past `WIDGET_HOST_TOKEN_FETCH_TIMEOUT_MS` never blocks the next send; `reason: answer` is the reply to its own answer / edit / undo frame. Runbook: `docs/runbooks/actions.md`.

## Hard bans

- `console.log`, `any`, `@ts-ignore`/`as any` as a fix
- Types or Zod schemas defined outside `packages/schemas`
- Skipping a layer, or an authenticated route outside `_authenticated/`
- A client-supplied `id`, or an internal `id` in any response/param — `publicId` only
- Installing a package without asking, or one with a native browser API equivalent
- Disabling an ESLint rule inline without asking
- A schema change without immediately running `db:generate`
- A mutation with an absent or empty `onError`
- Logging or persisting the host bearer token; calling a model provider outside the router
- From M1-5: `crypto.subtle` on company data outside `@app/crypto`; a plaintext secret in a DAL param, log or route response
- From M0-5: a tenant query outside `withTenant` (or `withPlatform` for cross-company work)
- From M1-3: code under test on the owner connection; a table without its `diletta_app` grant and RLS policies; `withPlatform` for one company's data
- From M1-9: DDL rights or an owner connection string for the worker; a `SECURITY DEFINER` function without a fixed `search_path`, or executable by `PUBLIC`
- From M1-8: a `/dashboard/*` or `/operator/*` route without `authorizeCompany` / `authorizePlatform` (except `GET /dashboard/me`); app code inserting an `admins` row with no company
- `npm`/`yarn` — `pnpm` always
